# Maintaining vendored rate data

Every price this library returns comes from data vendored under
`src/nem_rates/data/`. There is no runtime network access, which means keeping
prices correct is entirely a matter of keeping that vendored data current. It
has two update paths, depending on which table changed.

## Export rates (NBT matrices + holiday calendar): automated

`src/nem_rates/data/export/pge/*.json.gz`, `holidays.toml`, and
`manifest.json` are all generated by `tools/regen_data.py` from PG&E's
published export-rate archive. **Never hand-edit these files**; regenerate
them instead.

```bash
# Regenerate from a local copy of the archive
python tools/regen_data.py --zip /path/to/PGE-Solar-Billing-Plan-Export-Rates.zip

# Or download it directly
python tools/regen_data.py --download

# CI-style check: exit 1 if upstream has moved, without writing anything
python tools/regen_data.py --download --check
```

The script converts each row from UTC to Pacific time before bucketing, and
asserts that every one of the 576 cells per year (12 months x 2 day types x
24 hours) resolves to exactly one value: a lossless collapse, verified cell
by cell, not assumed.

After regenerating, run:

```bash
uv run pytest tests/test_export_golden.py
```

This round-trips the new matrices against known-good rows sampled verbatim
from PG&E's own files, deliberately including both DST transitions, an
observed holiday, and the Pacific/UTC year boundary, so a bad collapse fails
loudly rather than shipping silently.

A weekly CI job (`.github/workflows/rate-data-check.yml`) runs `--check` and
opens an issue if upstream has moved, so drift surfaces automatically rather
than waiting to be noticed. Export files are updated by **October 1** of any
year the CPUC adopts a new Avoided Cost Calculator.

## Retail tariff, ACC Plus, and CCA rate cards: manual

`src/nem_rates/data/tariff/pge/eelec/*.toml`, `export/pge/acc_plus.toml`, and
`cca/*.toml` are **hand-transcribed** from PG&E/CCA tariff PDFs. There is no
script for these because PG&E does not publish them as machine-readable data.
Retail rates change more often than export rates, via advice letters, three
times in the first half of 2026 alone, so this is the path you will likely
need more often.

When an advice letter or rate card update changes one of these tables:

1. **Add a new dated file rather than editing the current one**, e.g. a new
   `src/nem_rates/data/tariff/pge/eelec/2027-01-01.toml` with the new
   `effective` date and `advice_letter`. `RetailTariff` / `load_snapshot`
   always resolve to the latest snapshot whose `effective` date is on or
   before the moment being priced, so old snapshots, and old bills, keep
   resolving to the rate that was actually in force at the time.

   Adding a whole **schedule** works the same way: a new directory named for
   the tariff with `-` stripped (`E-TOU-C` → `etouc`) needs no code change.
   Omit `[periods].part_peak` if the schedule has none, and omit `[discounts]`
   if the sheet does not publish CARE/FERA percentages — a requested discount
   then raises rather than borrowing another schedule's figure.
2. Transcribe each unbundled component from the tariff sheet, then fill in
   `[totals]` from the sheet's own published totals.
   `tests/test_eelec.py::test_components_sum_to_published_total` asserts the
   components sum to the total exactly, which is what catches a mistyped
   digit during transcription.
3. For a CCA rate card (e.g. `mce.toml`), cite the source URL/PDF in a
   comment, and update `tests/test_mce.py` (or add an equivalent test) to pin
   the new values, ideally reconciled against a real bill, the way the
   existing MCE tests are.
4. Run the affected tests and fix any other hardcoded dollar figures the
   suite pins against the previous rates:

   ```bash
   uv run pytest tests/test_eelec.py tests/test_mce.py
   uv run pytest  # tests/test_engine.py, test_integrations.py, and
                  # test_mqtt_publisher.py all assert specific totals too
   ```

## Data sources

| Data | Source |
|---|---|
| Export rates (NBT) | [`PGE-Solar-Billing-Plan-Export-Rates.zip`](https://www.pge.com/assets/pge/docs/vanities/PGE-Solar-Billing-Plan-Export-Rates.zip), linked from `pge.com/eecvalues` |
| E-ELEC retail rates | [Schedule E-ELEC tariff sheet](https://www.pge.com/tariffs/assets/pdf/tariffbook/ELEC_SCHEDS_E-ELEC.pdf) |
| E-TOU-C retail rates and baseline quantities | [Schedule E-TOU-C tariff sheet](https://www.pge.com/tariffs/assets/pdf/tariffbook/ELEC_SCHEDS_E-TOU-C.pdf) |
| EV2-A retail rates | [Schedule EV2 tariff sheet](https://www.pge.com/tariffs/assets/pdf/tariffbook/ELEC_SCHEDS_EV2%20(Sch).pdf) |
| PCIA vintages | Schedule E-ELEC, Sheet 5 ("Vintage Power Charge Indifference Adjustment") |
| Franchise fee vintages | [Schedule E-FFS](https://www.pge.com/tariffs/assets/pdf/tariffbook/ELEC_SCHEDS_E-FFS.pdf), residential row |
| ACC Plus adder | PG&E Schedule NBT |
| Holiday calendar | Extracted from the `DayStart == 8` rows of the export files |
| MCE generation rates | [MCE residential rate table](https://mcecleanenergy.org/compare-rates-and-options/) |

OpenEI's URDB is deliberately **not** used as a source. Its `sell` field is a
scalar per period and cannot represent a 576-value export matrix, and its
E-ELEC record misfiles the October–December weekday peak hours as summer
off-peak, which yields wrong winter peak prices.
