# Maintaining vendored rate data

Every price this library returns comes from data vendored under
`src/nem_rates/data/`. There is no runtime network access, which means keeping
prices correct is entirely a matter of keeping that vendored data current. It
has two update paths, depending on which table changed.

## Export rates (NBT matrices + holiday calendar): automated

`src/nem_rates/data/export/pge/*.json.gz`, `holidays.toml`, and
`manifest.json` are all generated by `tools/regen_data.py` from PG&E's
published export-rate archive. **Never hand-edit these files**; regenerate
them instead.

```bash
# Regenerate from a local copy of the archive
python tools/regen_data.py --zip /path/to/PGE-Solar-Billing-Plan-Export-Rates.zip

# Or download it directly
python tools/regen_data.py --download

# CI-style check: exit 1 if upstream has moved, without writing anything
python tools/regen_data.py --download --check
```

The script converts each row from UTC to Pacific time before bucketing, and
asserts that every one of the 576 cells per year (12 months x 2 day types x
24 hours) resolves to exactly one value: a lossless collapse, verified cell
by cell, not assumed.

After regenerating, run:

```bash
uv run pytest tests/test_export_golden.py
```

This round-trips the new matrices against known-good rows sampled verbatim
from PG&E's own files, deliberately including both DST transitions, an
observed holiday, and the Pacific/UTC year boundary, so a bad collapse fails
loudly rather than shipping silently.

A weekly CI job (`.github/workflows/rate-data-check.yml`) runs `--check` for
**both** the export rates and the retail tariffs and opens an issue if either
has moved, so drift surfaces automatically rather than waiting to be noticed.
Export files are updated by **October 1** of any year the CPUC adopts a new
Avoided Cost Calculator; retail rates change more often, via advice letters —
three times in the first half of 2026 alone.

## Retail tariff sheets: automated

`src/nem_rates/data/tariff/pge/*/*.toml` are generated by
`tools/regen_tariff.py` from PG&E's published tariff sheets. **Do not hand-edit
the rate tables**; regenerate them.

```bash
python tools/regen_tariff.py --schedule all --download
python tools/regen_tariff.py --schedule eelec --pdf /path/to/sheet.pdf
python tools/regen_tariff.py --schedule all --download --check   # CI-style
```

The sheets are more machine-readable than they look: every rate line is a label
followed by one figure per time-of-use period, negatives in parentheses and an
optional `(I)`/`(R)`/`(N)`/`(L)` change marker per cell.

Two checks gate every write, and either failing refuses to produce a file:

1. **The components must sum to the sheet's own published totals**, which live
   in a different table on a different page. This is the check that used to
   catch hand-transcription slips; it now catches mis-parses, and a silent one
   would have to be wrong in two tables in exactly compensating ways.
2. **The library must be able to price what was generated.** The generator
   writes key names and `nem_rates.tariff.retail` reads them back, two
   independent encodings of one schema that could drift apart silently. So the
   rendered file is handed to a real `RetailTariff` and the price it computes is
   compared against the published total.

### What it does not generate

A sheet publishes rates, not structure. Season boundaries, time-of-use period
hours, `has_baseline`, which components a CCA customer drops, and the franchise
fee vintages (Schedule E-FFS, a different document) are **carried forward from
the previous snapshot**. A structural change is still a human edit, and should
be.

### Sheets revise independently

A tariff book is a compilation and its pages carry their own advice letters. On
all three schedules the totals page is Advice 7921-E effective 2026-06-01 while
the unbundled rate table is 7846-E effective 2026-03-01, and the two reconcile
exactly, so the values have been in force since March.

The snapshot is dated from **the sheet carrying the rates**, not the latest date
in the book. That is not cosmetic: `effective` is what `load_snapshot` resolves
against, so dating a snapshot later than its rates took force leaves a hole
where an April bill either prices from superseded rates or fails outright. Hand
transcription had reached both answers from the same evidence -- E-ELEC and
E-TOU-C were dated June, EV2-A March -- which is the kind of inconsistency the
generator exists to remove.

## ACC Plus and CCA rate cards: still manual

`export/pge/acc_plus.toml` and `cca/*.toml` remain **hand-transcribed**.

`cca/mce.toml` is the notable gap: MCE publishes a residential rate table as a
PDF and its Solar Billing Plan terms as another, so the same extraction approach
would work, but nothing automates it today. What stands in for it is
`tests/test_mce.py`, which pins every value and asserts the parity with PG&E's
generation component that currently holds -- so an MCE divergence fails loudly
even though it will not be noticed automatically.

When an advice letter or rate card update changes one of these tables:

1. **Add a new dated file rather than editing the current one**, with the new
   `effective` date and `advice_letter`. `RetailTariff` / `load_snapshot`
   always resolve to the latest snapshot whose `effective` date is on or
   before the moment being priced, so old snapshots, and old bills, keep
   resolving to the rate that was actually in force at the time. For tariff
   sheets `regen_tariff.py` does this for you, naming the file from the sheet's
   own effective date.

   Adding a whole **schedule** works the same way: a new directory named for
   the tariff with `-` stripped (`E-TOU-C` → `etouc`) needs no code change, plus
   an entry in `SCHEDULES` in `regen_tariff.py`. Omit `[periods].part_peak` if
   the schedule has none, and omit `[discounts]` if the sheet does not publish
   CARE/FERA percentages — a requested discount then raises rather than
   borrowing another schedule's figure.
2. Transcribe each unbundled component from the tariff sheet, then fill in
   `[totals]` from the sheet's own published totals.
   `tests/test_eelec.py::test_components_sum_to_published_total` asserts the
   components sum to the total exactly, which is what catches a mistyped
   digit during transcription.
3. For a CCA rate card (e.g. `mce.toml`), cite the source URL/PDF in a
   comment, and update `tests/test_mce.py` (or add an equivalent test) to pin
   the new values, ideally reconciled against a real bill, the way the
   existing MCE tests are.
4. Run the affected tests and fix any other hardcoded dollar figures the
   suite pins against the previous rates:

   ```bash
   uv run pytest tests/test_eelec.py tests/test_mce.py
   uv run pytest  # tests/test_engine.py, test_integrations.py, and
                  # test_mqtt_publisher.py all assert specific totals too
   ```

## Data sources

| Data | Source |
|---|---|
| Export rates (NBT) | [`PGE-Solar-Billing-Plan-Export-Rates.zip`](https://www.pge.com/assets/pge/docs/vanities/PGE-Solar-Billing-Plan-Export-Rates.zip), linked from `pge.com/eecvalues` |
| E-ELEC retail rates | [Schedule E-ELEC tariff sheet](https://www.pge.com/tariffs/assets/pdf/tariffbook/ELEC_SCHEDS_E-ELEC.pdf) |
| E-TOU-C retail rates and baseline quantities | [Schedule E-TOU-C tariff sheet](https://www.pge.com/tariffs/assets/pdf/tariffbook/ELEC_SCHEDS_E-TOU-C.pdf) |
| EV2-A retail rates | [Schedule EV2 tariff sheet](https://www.pge.com/tariffs/assets/pdf/tariffbook/ELEC_SCHEDS_EV2%20(Sch).pdf) |
| PCIA vintages | Schedule E-ELEC, Sheet 5 ("Vintage Power Charge Indifference Adjustment") |
| Franchise fee vintages | [Schedule E-FFS](https://www.pge.com/tariffs/assets/pdf/tariffbook/ELEC_SCHEDS_E-FFS.pdf), residential row |
| ACC Plus adder | PG&E Schedule NBT |
| Holiday calendar | Extracted from the `DayStart == 8` rows of the export files |
| MCE generation rates | [MCE residential rate table](https://mcecleanenergy.org/compare-rates-and-options/) |

OpenEI's URDB is deliberately **not** used as a source. Its `sell` field is a
scalar per period and cannot represent a 576-value export matrix, and its
E-ELEC record misfiles the October–December weekday peak hours as summer
off-peak, which yields wrong winter peak prices.
